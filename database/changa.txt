 Written 17 September 2026, with the sales-return / invoice-PDF / warehouse work.

 Nothing in this file is optional if you want that work to run. Everything in
 it is a setting, a migration or a click — there is no code left to write.

 Read section 1 before you deploy anything. Four things; the first is already
 done on Neon and the other three are yours. Ten minutes in all.

 1.2  EVERYBODY SIGNS OUT AND BACK IN — the same day

      Permissions travel INSIDE the JWT, as "perm" claims, and a token lasts
      eight hours (Jwt:ExpiryMinutes = 480). A salesperson holding a token
      issued before the migration still carries the old five permissions, and
      will go on being refused the invoice screen until it expires.

      Signing out and back in fixes it immediately. Doing nothing fixes it by
      tomorrow morning. There is no server-side way to force it short of
      rotating Jwt:Key, which would sign everybody out including you.


 1.3  SET THE WEBSITE ADDRESS ON THE API HOST

      New setting, because every notification now carries a real link instead
      of a bare path like "/sales/orders/42":

          App__WebBaseUrl = https://advpos-frontend.vercel.app

      Set it as an ENVIRONMENT VARIABLE wherever the API runs (Railway →
      Variables). The double underscore is ASP.NET's own convention for
      nesting; it overrides the value committed in appsettings.json, which is
      already set to the same thing as a fallback.

      Change this one line and every notification, every push and every link in
      the bell follows it. That was the point of asking for it.

      WHY IT MATTERS: a Web Push payload is opened by the service worker with
      clients.openWindow(). A bare path there resolves against the worker's own
      scope rather than against your site — it happens to work while the app is
      the only thing on that origin and stops working the day it is not. And
      when somebody forwards a notification to a colleague, a path is not a
      link at all.

      In-app it still behaves as it always did: the bell turns a link back into
      a path when it points at the site you are already on, so clicking one
      does not reload the whole application.


 1.4  ADD THE VERCEL ORIGIN TO CORS — probably already done, check anyway

      appsettings.json now lists it:

          "Cors": { "AllowedOrigins": [ ..., "https://advpos-frontend.vercel.app" ] }

      It was NOT there before: the list was localhost:3000, localhost:3000 over
      https, and www.vizo.com.pk. If the live frontend has been working, then
      something on the host is already overriding this — check for a
      Cors__AllowedOrigins__3 variable and make sure the two do not disagree.

      A missing origin fails the browser's pre-flight before any of our code
      runs, which looks exactly like a broken API and is not one.

 2.2  TEN INVOICES HAVE NO STORED PDF

      Of 38 sale invoices, 10 have no PdfUrl at all. Nothing is broken — the
      API renders a bill from the database whenever one is asked for, so Print
      works on all of them. They simply have no archived copy.

      Opening each one archives it. Or press "Rebuild" on the invoice screen.
      No hurry.

 2.3  PDF DELIVERY IS ON, AND THE APP NOW NOTICES

      Cloudinary blocks PDF delivery by default on accounts created since 2023.
      convey.txt has said for weeks that both of this project's accounts were
      in that state. CHECKED TODAY, and it is no longer true:

          HEAD .../advpos/documents/invoices/INV-26-8887_u7qavn.pdf → 200 OK

      Somebody has ticked the box. Good — that is the better link to hand out.

      The app used to ignore the question entirely and always open the
      Cloudinary URL, which is why Print showed an error page during the months
      the answer was no. It now stores the answer per invoice and uses it. The
      first time each old bill is opened it spends one HEAD request finding out
      and writes it down; after that it goes straight to Cloudinary.

      If you ever untick it, nothing breaks — the API serves the bytes itself.

      Six invoices are already flagged deliverable: the six raised above, plus
      one re-checked while testing. The other 32 flip the first time somebody
      opens them.

 4.  STILL UNFIXED, FROM AN OLDER CONVEY — one line, your call
───────────────────────────────────────────────────────────────────────────────

  vizo-erp/.env.example carries a VAPID public key that does NOT match the
  server's. .env.local is correct, so push works today; the danger is that
  anybody setting up a new machine by copying the template gets a browser that
  subscribes happily and a server that then rejects every send — silently.

  The fix is to copy VapidSettings:PublicKey out of appsettings.json into
  .env.example. Still not done, because a key is not mine to change and
  changing the wrong one of the two breaks the setup that works.
