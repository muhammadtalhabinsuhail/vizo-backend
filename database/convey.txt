 1.  THINGS THAT WILL BREAK IF YOU SKIP THEM
───────────────────────────────────────────────────────────────────────────────

 1.1  RUN THE MIGRATIONS

      backend/database/15_order_workflow.sql
      backend/database/16_warehouse_and_notification_links.sql

      Both have already been run against the live Neon database. Any OTHER
      environment — a colleague's local copy, staging — must run them or the
      order chain and the clickable bell are simply missing.

      15 adds four order statuses, the warehouse-keeper role, the
      orders.warehouse permission, "OrderChangeRequest", and
      "SalesOrder"."ConfirmRemindedAt".

      16 adds the "Seen by Warehouse" status (and renumbers the chain to ten
      steps), the "Notification"."Url" column, and invoices.view for the
      warehouse keeper.

      Both are written to be safe to run twice.

 1.2  npm install IN THE FRONTEND

      The live bell needs @microsoft/signalr, which is in package.json. Without
      `npm install` the build fails on an import it cannot resolve.

      It is loaded with a dynamic import() inside the effect, not at the top of
      the file, so it lands in its own chunk rather than the shared bundle —
      AGENTS.md rule 4. Do not "tidy" it into a normal import.

 1.3  YOUR LOGIN FIX IS NOT IN THIS REPOSITORY

      You said you had fixed the login screen by hand so the warehouse keeper
      could sign in. There is no such change in the working tree — src/app/
      login/page.tsx still lists four panels (Sales, Order Department,
      Accountant, Super Admin) and no warehouse one, and git reports no local
      edits to it.

      So either it was made in a different copy of the project, or it has been
      lost. Nothing here has overwritten it — there was nothing to overwrite —
      but please check before you pull, because a pull WILL overwrite an
      uncommitted change if one turns up later.

      For what it is worth, the panels are only a convenience that fills in an
      e-mail address. Typing the address by hand signs the keeper in just the
      same. The account is real: UserId 41, Talha,
      muhammadtalhabinsuhail@gmail.com, role warehouse-keeper, active.

 2.  A BUG I FOUND AND DID NOT TOUCH
───────────────────────────────────────────────────────────────────────────────

 2.1  THE VAPID KEYS IN .env.example DO NOT MATCH THE SERVER

      vizo-erp/.env.example       NEXT_PUBLIC_VAPID_PUBLIC_KEY=BFkgyKlQ1rBMwE-...
      backend appsettings.json    VapidSettings:PublicKey     =BLDLEeGrO9V8jS1...

      Two different key pairs.

      .env.local is correct — it matches the server, so push works today. The
      danger is the template: anybody setting up a new machine by copying
      .env.example to .env.local gets a browser that subscribes to push quite
      happily and a server that is then rejected on every send. It fails
      silently, which is the worst way for it to fail.

      Left alone because a key is not mine to change and changing the wrong one
      of the two would break the working setup. The fix is one line: copy the
      public key out of appsettings.json into .env.example.


───────────────────────────────────────────────────────────────────────────────
 3.  BUGS I DID FIX, THAT YOU DID NOT ASK ABOUT
───────────────────────────────────────────────────────────────────────────────

 3.1  NOTIFICATION BODIES OVER 300 CHARACTERS WERE BEING THROWN AWAY

      The bell truncated the body to 400 characters. The column is
      VARCHAR(300). A long notification therefore threw on the way in — and
      because PushNotificationService swallows its own failures, it did so
      without a word: no bell row, no push, no log line. Now truncated to 300.

 3.2  AN ERROR MESSAGE WITH A WINDOWS PATH IN IT

      NotificationController said it could not "load C:/Program Files/Git/api/
      notification". A Git Bash path expansion had been baked into the source
      at some point. It now says "load your notifications".

 3.3  EDITING AN ORDER CRASHED INSTEAD OF REFUSING

      UpdateOrder read order.Status without including it, so the check meant to
      refuse a delivered order threw a NullReferenceException on every single
      edit. Fixed by including the navigation.


───────────────────────────────────────────────────────────────────────────────
 4.  WHAT THE NOTIFICATIONS DO NOW
───────────────────────────────────────────────────────────────────────────────

 4.1  EVERY ONE OF THEM GOES SOMEWHERE

      The link always existed — all fifty-odd call sites passed one — but it
      was only ever handed to Web Push. A notification read in the bell was a
      dead end: it told you an order had been confirmed and left you to go and
      find it.

      "Notification"."Url" now stores it, the API returns it, and a row in the
      bell is a real anchor. Middle-click and "open in new tab" work.

      ROWS WRITTEN BEFORE THIS HAVE NO LINK and are not clickable. Nothing is
      broken; they simply predate the column. New ones all have one.

 4.2  WHO GETS TOLD WHAT

      Every action taken by anybody other than the Super Admin now reaches the
      Super Admin's bell, named, with the thing it is about and a link to it:

        VIZO — New item added by Talha
        VIZO Warehouse Test Charger (TEST-WH-01) is now in the catalogue.
        -> /inventory/products/38

      Newly covered, where there was nothing before: adding or editing a
      product; adding, renaming or deleting a category or brand; opening,
      editing or closing a customer/supplier account; writing, editing or
      deleting a journal entry; editing or deleting a voucher; editing or
      deleting an expense; reopening a closed period.

      Deliberately NOT covered, because the noise would cost more than the
      information: marking a notification read, uploading a file, archiving a
      PDF, asking the reports screen a question, and everything under /admin
      that only the Super Admin can do anyway — telling them about their own
      clicks helps nobody.

 4.3  THE ORDER CHAIN, AND WHO HEARS EACH STEP

        4 Invoiced           -> Admin, Accounts
        5 Seen by Warehouse  -> Admin, and the rep whose order it is
        6 On way to Order Dept -> Admin, ORDER DEPARTMENT, and the rep
        7 Received at Order Dept -> Admin, Warehouse
        8 Packaging          -> Admin, and the rep
        9 Dispatched         -> Admin, the rep, Accounts
       10 Delivered          -> Admin, Accounts

      The rep is added by user id, not by role, so it is the person who wrote
      that order rather than every salesperson in the company.


───────────────────────────────────────────────────────────────────────────────
 5.  THE WAREHOUSE KEEPER, EXACTLY
───────────────────────────────────────────────────────────────────────────────

 CAN:  see every order in the system, open any invoice, print a bill, and make
       two moves — and only these two, only on an INVOICED order:

         Invoiced -> Seen by Warehouse -> On way to Order Dept

 CANNOT: raise an order, edit one, delete one, cancel one, ask permission to do
       any of those, or move an order to any other status. There is no "Ask for
       permission" button for this role — editing is not part of the job, so a
       button that asks for it is asking for something that will never be
       granted.

 Verified against the live API rather than assumed. On an invoiced order the
 keeper is offered exactly one action; on a draft, a dispatched or a delivered
 order, none at all. POST, PUT and DELETE on an order all answer 403, as does
 trying to skip from Invoiced to Delivered.

 The "Set status" dropdown is hidden for this role, because its only entry
 would repeat the button beside it.

 NOTE: the keeper CAN add items to the catalogue today, because the whole
 inventory controller is open to the back office rather than gated item by
 item. Your example assumed that, so I left it. If you would rather they could
 not, untick it in Setup → Roles once the catalogue endpoints are
 permission-gated — say the word and that is a small change.


───────────────────────────────────────────────────────────────────────────────
 6.  DECISIONS YOU MIGHT WANT DIFFERENTLY
───────────────────────────────────────────────────────────────────────────────

 6.1  THE WAREHOUSE STARTS AT INVOICED, NOT AT CONFIRMED

      It used to pick up a CONFIRMED order. It no longer does, because you
      asked for the two new steps to open "after the status Invoiced", and
      because picking stock against an order the office has not billed is how
      goods leave with no invoice behind them.

      If you want the floor to be able to start before the paperwork, it is one
      line in Services/OrderWorkflow.cs — the Moves table.

 6.2  PERMISSIONS NOW REALLY OPEN PAGES

      Endpoints used to be guarded by hard-coded lists of ROLE NAMES, so
      ticking a box in Setup → Roles saved happily and changed nothing.
      Authorisation is now on the permission itself. Worth a look over
      Setup → Roles to check that what is ticked is what you meant, because
      until recently some of it had no effect.

 6.3  A SALESPERSON SEES ONLY THEIR OWN WORK

      Orders, invoices and returns are filtered to the signed-in rep, on the
      list AND on the detail endpoint. Accounts, the order desk, the warehouse
      and the owner see everything.

 6.4  A REP CANNOT INVOICE THEIR OWN NEW ORDER

      The "raise the invoice too" switch on the new-order screen is ignored for
      the Sales role, because it stepped straight over your confirmation. The
      reply says so. One line in CreateOrder if you disagree.

 6.5  DELETING AN INVOICED ORDER IS REFUSED — EVEN FOR YOU

      It would leave an invoice pointing at nothing. Raise a sales return
      instead. Everything else — any status, either direction, edit, delete —
      is yours without restriction.

 6.6  THE ORDER DATE IS NOT EDITABLE

      Editing a quantity corrects a mistake. Moving the date an order was
      placed rewrites history. The API refuses it.


───────────────────────────────────────────────────────────────────────────────
 7.  THE DATE BUG — WHAT IT ACTUALLY WAS
───────────────────────────────────────────────────────────────────────────────

 An order taken on the night of 3 September was stored as 2 September.

 Every date came from DateTime.UtcNow. Pakistan is UTC+5, so between midnight
 and 5am our time it is still yesterday in UTC.

 Fixed by putting the business clock in one place —
 backend/vizo-backend/Services/BusinessClock.cs — and sweeping the seventeen
 other callers of UtcNow, including document numbering, which was stamping the
 wrong YEAR on every 1 January.

 EXISTING ROWS ARE NOT CORRECTED. Anything already stored with the wrong date
 still has it. If that matters, say so — it needs a decision about which rows,
 because not every early-morning date is wrong.

 10.  THE INVOICE
───────────────────────────────────────────────────────────────────────────────

 In backend/vizo-backend/Documents/InvoicePdf.cs:

   · a PACKING column between DESCRIPTION and QTY, showing Product.Packing and
     a dash for anything sold loose
   · SALESMAN: under the FROM block, naming whoever wrote the ORDER — not
     whoever cut the invoice, because the customer wants the rep
   · the navy is #0B2545 rather than #031833, which on a laser printer came out
     as a slab of toner; the table header is a clear step lighter than the
     banner instead of almost the same dark; the two background tints now
     differ enough to be doing different jobs; the yellow is a thin accent rule
     rather than a fill

 An invoice REBUILDS ITSELF when its order is edited — lines, totals, and the
 stored PDF thrown away so the next print is the new figures. The invoice
 number never changes.
