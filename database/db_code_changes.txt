 SECTION 0 — IDENTITY SEQUENCES RESET      [ALREADY APPLIED]  ** READ THIS **
═══════════════════════════════════════════════════════════════════════════════

 THIS WAS THE SINGLE BIGGEST BUG IN THE PROJECT. Nothing could be created
 anywhere in the application before it was fixed — not a customer, not an
 order, not a product, not a voucher.

 WHY
   The seed data was loaded with EXPLICIT primary keys:

       INSERT INTO "Product" ("ProductId", ...) VALUES (1, ...), (2, ...) ...

   Postgres only advances an identity sequence when it actually generates a
   value. Supplying the key yourself never touches it, so every sequence was
   still parked at 1 while the tables held rows numbered up to 106.

   The first row the API tried to insert asked the sequence for an id, got 1,
   and collided with seeded row 1:

       23505: duplicate key value violates unique constraint "SalesReturn_pkey"

   Measured on Neon on 2026-08-25: 77 OF 78 identity sequences were behind
   their table's max id.

   The original 03_sequence_reset.sql was written for exactly this, but it is
   the snake_case version and was never applied to Neon.

 WHAT WAS RUN
   backend/database/07_neon_sequence_reset.sql — a DO block that walks every
   identity column in the public schema and setvals its sequence to the table's
   current max id, so the next generated value is max + 1. It is idempotent:
   run it again any time you import data with explicit keys.

 RESULT
   sequences checked: 78, advanced past real data: 77

 VERIFIED
   POST /api/parties created "Sequence Reset Probe" as UserId 33 (next after
   the seeded max of 32), the row was confirmed present in Neon, ActivityLog
   recorded PARTY_CREATED, and the probe row was then deleted.

 ⚠ IF YOU RE-IMPORT SEED DATA WITH EXPLICIT IDs, RUN 07 AGAIN or every create
   in the application starts failing with duplicate-key errors again.

 SECTION 1 — NEW TABLE: "PasswordResetCode"          [ALREADY APPLIED]
═══════════════════════════════════════════════════════════════════════════════

 WHY
   AuthController.cs implements the forgot-password flow and reads/writes a
   table called "PasswordResetCode". That table did not exist on Neon, so
   every call to POST /api/auth/forgot-password threw

       42P01: relation "PasswordResetCode" does not exist

   This is the ONLY table this work added. The other 84 are untouched.

 DESIGN NOTE
   A BCrypt HASH of the six digits is stored, never the digits themselves —
   a leaked table must not hand somebody a working reset code. "Attempts" is
   what stops a six-digit code being brute forced: the endpoint refuses the
   code once it reaches PasswordReset:MaxAttempts (5) and the row is dead.

-------------------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS "PasswordResetCode" (
    "ResetId"    INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "UserId"     INT          NOT NULL,
    "CodeHash"   VARCHAR(200) NOT NULL,
    "ExpiresAt"  TIMESTAMP    NOT NULL,
    "ConsumedAt" TIMESTAMP    NULL,
    "Attempts"   SMALLINT     NOT NULL DEFAULT 0 CHECK ("Attempts" >= 0),
    "CreatedAt"  TIMESTAMP    NOT NULL,
    CONSTRAINT fk_prc_user FOREIGN KEY ("UserId")
        REFERENCES "User" ("UserId") ON UPDATE CASCADE ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS "ix_prc_user" ON "PasswordResetCode" ("UserId");
-------------------------------------------------------------------------------

 ROLLBACK (if you want it gone)
     DROP TABLE IF EXISTS "PasswordResetCode";
   Then delete backend/vizo-backend/Models/PasswordResetCode.cs and
   backend/vizo-backend/Models/AppDbContext.Custom.cs, and remove the
   forgot-password / verify-code / reset-password actions from AuthController.

 EF SIDE (already in the repo, no migration needed)
   The scaffolded AppDbContext.cs is NOT edited. The new entity is attached
   through the OnModelCreatingPartial hook the scaffolder leaves behind:
       Models/PasswordResetCode.cs      — the entity
       Models/AppDbContext.Custom.cs    — DbSet + Fluent mapping
   IF YOU RE-SCAFFOLD, DELETE BOTH FILES FIRST. The table now exists, so
   Scaffold-DbContext will generate its own copies and you will get
   duplicate-definition compile errors.

 3.1  DOCUMENT NUMBER COLLISIONS
 ------------------------------------------------------------------------------
 The API allocates document numbers by reading and incrementing
 "DocumentSeries"."NextNumber" in a single call (NextNumber() in
 SalesController / AccountingController / DispatchController). Two documents
 created in the same instant can take the same number: the read and the write
 are not atomic against another connection.

 It has not bitten anyone yet because throughput is low. The proper fix is one
 PostgreSQL sequence per series, which is a real schema change and is therefore
 NOT applied here. If you want it:

   -- for each row in "DocumentSeries", e.g. the sales-order series:
   -- CREATE SEQUENCE IF NOT EXISTS seq_docseries_so START WITH 145;
   -- then have the API call nextval('seq_docseries_so') instead of
   -- reading/updating "NextNumber".

 An interim fix needing no schema change is to wrap the read-and-increment in
   SELECT ... FOR UPDATE
 inside the same transaction as the document insert.


 3.2  OPENING BALANCES DO NOT BALANCE
 ------------------------------------------------------------------------------
 This is a DATA observation, not a bug, and nothing was changed.

   Posted journal movement balances exactly:
     SELECT sum(l."DebitAmount"), sum(l."CreditAmount")
     FROM "JournalEntryLine" l
     JOIN "JournalEntry" e ON e."EntryId" = l."EntryId"
     JOIN "PostingStatus" s ON s."StatusId" = e."StatusId"
     WHERE s."StatusKey" = 'POSTED';
     -- 5,323,575.00 = 5,323,575.00   difference 0.00   ✓

   The seeded OPENING balances do not:
     SELECT sum(CASE WHEN t."IsDebitNormal" THEN a."OpeningBalance"
                     ELSE -a."OpeningBalance" END)
     FROM "Account" a JOIN "AccountType" t ON t."AccountTypeId" = a."AccountTypeId";
     -- 51,256,709.00 out on a debit basis

 GET /api/accounting/trial-balance now reports the two figures separately, so
 nobody goes hunting through journal entries that were never at fault. If these
 are real migrated opening balances they need a balancing entry (usually to
 Owner Capital or a suspense account) before the books can be trusted:

   -- INSERT a journal entry debiting/crediting a suspense account for
   -- 51,256,709.00 to bring the opening position into balance.

 SECTION 5 — "CLM" DOCUMENT SERIES  (needed by the new POST /api/claims)
═══════════════════════════════════════════════════════════════════════════════

 WHO NEEDS IT
   The claims screen can now receive a claim (Daily Work → Claims → "Receive
   Claim"). It calls POST /api/claims, which asks NextNumber("CLM") for the
   claim number.

 THE PROBLEM
   "DocumentSeries" has rows for ORD, INV, SR, PO, GRN, PI, PR, TRF, ADJ, RV,
   PV, JV and DLV — but none for CLM. NextNumber() falls back to a timestamp
   when a series is missing, so claims created through the app come out as
     CLM-20260825174238
   instead of matching the seeded claims, which read
     CLM-26-0142

   Nothing breaks. The number is unique and the claim is correct. It simply
   does not match the house format, and it will keep not matching until this
   row exists.

 THE FIX — one INSERT, safe to re-run
   Run this once against Neon. NextNumber picks it up immediately; no restart.

     INSERT INTO "DocumentSeries"
         ("DocumentType", "Prefix", "NextNumber", "Padding", "IncludeYear")
     SELECT 'Claim', 'CLM', 143, 4, true
     WHERE NOT EXISTS (
         SELECT 1 FROM "DocumentSeries" WHERE "Prefix" = 'CLM'
     );

   NextNumber starts at 143 because the highest seeded claim is CLM-26-0142.
   Check the column list against the live table first — it was read from the
   scaffolded model, not from a describe:

     SELECT column_name, data_type, is_nullable
     FROM information_schema.columns
     WHERE table_name = 'DocumentSeries'
     ORDER BY ordinal_position;

   If the table carries extra NOT NULL columns, add them to the INSERT.

 ROLLBACK
     DELETE FROM "DocumentSeries" WHERE "Prefix" = 'CLM';

 STATUS: ⛔ NOT APPLIED — this is a write to the live database, so it is left
         for you to run rather than done silently.

 6.2  "SIGN OUT EVERYWHERE"
      The API issues a stateless JWT and keeps no record of it, so there is
      nothing to revoke — a token stays valid until it expires no matter what
      any button does. The cheapest honest fix is a token version:

        ALTER TABLE "User" ADD COLUMN "TokenVersion" integer NOT NULL DEFAULT 0;

      AuthController would then stamp the current value into the JWT at login
      and compare it on every request; "sign out everywhere" is an increment.
      That is a change to AuthController.cs, which is Talha's file — his call,
      not something to do behind him.

      Rollback: ALTER TABLE "User" DROP COLUMN "TokenVersion";

 SECTION 9 — 2026-08-26 — STALE DROPDOWNS: ROOT CAUSE AND FIX
═══════════════════════════════════════════════════════════════════════════════

 NO SCHEMA CHANGE WAS NEEDED, AND NO NEW TABLE OR MODEL WAS CREATED.
 This section is here because section 5 of the brief asks for the dropdown
 investigation to be written down either way.

 THE REPORTED BUG
   A product created on the New Product screen did not appear in the product
   pickers on other screens (stock adjustment, stock transfer, purchase order
   line, and so on).

 WHAT IT WAS NOT
   Not a caching problem, not Next.js App Router route caching, and not a
   stale query on the server. Each of those was checked.

 WHAT IT ACTUALLY WAS
   Those screens were never connected. They imported a hard-coded TypeScript
   array from the frontend's own source:

       import { products } from "@/data/products";
       import { activeLocations } from "@/data/settings";
       import { parties } from "@/data/parties";

   That file is compiled into the bundle. It cannot change when the database
   changes, so no amount of refetching would ever have shown a new product --
   there was no fetch at all. GET /api/purchases/lookups was already returning
   the full live catalogue the whole time; the pages simply ignored it.

 PROOF
   Product id 35, SKU VZ-123-ER ("muhammadtalhabinsuhail"), was created through
   the app by Talha between sessions. It was absent from every picker before
   this change and present in all of them afterwards, with no restart.

 THE FIX (frontend, plus one small API addition)
   Every affected picker now fetches on mount with axios and renders from that
   response. Fixed in:

     components/widgets/report-toolbar.tsx   location filter -- SHARED by all
                                             seven report screens, so a
                                             location added at /admin/locations
                                             never appeared on any report
     inventory/adjustments/new               products, locations, reasons
     inventory/transfers/new                 products, both locations
     purchases/orders/new                    products, suppliers, locations
     purchases/grns/new                      open POs, PO lines, locations
     purchases/invoices/new                  products, suppliers, methods, POs
     purchases/returns/new                   posted invoices, invoice lines,
                                             locations

   The reason list on the adjustment form was six <option> tags written into
   the page while the API validates against the AdjustmentReason table, so a
   reason edited in the database would have been rejected on save. It reads
   the table now.

 API ADDITION FOR THIS
   GET /api/inventory/lookups gained a `products` array (active only). The
   adjustment and transfer pickers had no live product source before; the only
   one that existed was on the purchases controller, which is the wrong module
   to reach into from an inventory screen.

 HOW TO RE-TEST IT
   1. Create a product at /inventory/products/new.
   2. WITHOUT restarting anything, open each of:
        /inventory/adjustments/new    /inventory/transfers/new
        /purchases/orders/new         /purchases/invoices/new
   3. Open the item picker on each. The new product must be listed.
   4. Set it inactive at /inventory/products/<id> and repeat -- it must now be
      absent, which proves the filter and not just the fetch.
